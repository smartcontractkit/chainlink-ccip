# Implementation plan: EVM v1.5.0 TokenAdapter

Target: `tokens.TokenAdapterRegistry` resolves `("evm", 1.5.0)`, so `token_expansion` and every
other version-dispatched token changeset works against `BurnMintTokenPoolAndProxy 1.5.0` pools.

Baseline: written against `chainlink-ccip@5c5da7896`; **implemented against `d077fd910`** (see
[§7](#7-status--what-landed)). Companion doc:
[token-pool-version-coverage.md](token-pool-version-coverage.md).

> **Status: implemented.** All four open decisions were resolved as recommended. Backfilling
> additional target pools into the datastore is explicitly **out of scope** for this change — this
> is the core upgrade-enablement logic only. See [§7](#7-status--what-landed).

## 0. Three corrections to the brief, up front

These change the shape of the work. Everything below assumes them.

### 0.1 v1.5.1 is **not** a standalone adapter — it embeds a shared base

The brief says "1.5.1 / 1.6.1 / 2.0.0 are each independent structs with no shared base". They are
not. All three embed `v1_0_0/adapters.EVMPoolAdapter`:

```go
// chains/evm/deployment/v1_5_1/adapters/tokens.go:40
type TokenAdapter struct {
    evm1_0_0.EVMPoolAdapter
}

func NewTokenAdapter() *TokenAdapter {
    return &TokenAdapter{EVMPoolAdapter: evm1_0_0.EVMPoolAdapter{
        Ops:                &poolOpsV151{},        // version-specific contract calls
        DeployTokenPoolSeq: seqV1_5_1.DeployTokenPool,
    }}
}
```

`EVMPoolAdapter` (which itself embeds `EVMTokenBase`) already supplies
`DeriveTokenAddress`, `DeriveTokenDecimals`, `DeriveTokenPoolCounterpart`, `AddressRefToBytes`,
`ManualRegistration`, `SetTokenPoolRateLimits`, `SetTokenPoolAdmins`, `RemoveRemotePools`,
`DeployToken`, `DeployTokenVerify`, `DeployTokenPoolForToken`, `UpdateAuthorities`,
`GetOnchainRateLimits`, and the `TokenRefResolver` / `TokenAdminRegistryReader` implementations —
all version-agnostic, delegating anything version-specific to the injected `PoolOps`.

v1.5.1 overrides exactly four things: `ConfigureTokenForTransfersSequence` and the three
`TokenPoolMigrator` methods.

**So "mirror the v1.5.1 structure" means: embed `EVMPoolAdapter`, write a `poolOpsV150`, override
the same four methods.** Not 11 hand-written methods. This is less work than the brief assumes,
and it is what keeps the adapter from drifting.

### 0.2 The v1.5.0 pool ABI differs from v1.5.1 in ways that block the obvious copy-paste

Dumped from `BurnMintTokenPoolAndProxyABI` in
`chains/evm/deployment/v1_5_0/operations/burn_mint_token_pool_and_proxy/`:

| Capability | v1.5.1 | v1.5.0 `BurnMintTokenPoolAndProxy` | Impact |
|---|---|---|---|
| `getToken()` | ✓ | ✓ | — |
| `getSupportedChains()` | ✓ | ✓ | — |
| `getRemoteToken(uint64)` | ✓ | ✓ | — |
| `getTokenDecimals()` | ✓ | **✗** | `PoolOps.GetTokenDecimals` must read ERC20 `decimals()` off `getToken()` |
| `getRemotePools(uint64) → bytes[]` | ✓ | **✗** — only `getRemotePool(uint64) → bytes` | `GetRemotePools` shims singular → 1-element slice |
| `addRemotePool` | ✓ | **✗** | cannot append a second remote pool |
| `removeRemotePool` | ✓ | **✗** | `PoolOps.RemoveRemotePools` unsupportable |
| `setRemotePool(uint64,bytes)` | ✗ | ✓ | **replaces** the single remote pool |
| `applyChainUpdates` | `(uint64[] toRemove, ChainUpdate[] toAdd)`, `ChainUpdate.remotePoolAddresses [][]byte` | `(ChainUpdate[] chains)`, `ChainUpdate.remotePoolAddress []byte`, removal via `allowed=false` | different struct + call shape |
| `setChainRateLimiterConfig(uint64,cfg,cfg)` | ✓ | ✓ | — |
| `get/setRateLimitAdmin` | ✓ | ✓ | — |

Consequence: **`v1_5_1/sequences/token_pool.ConfigureTokenPoolForRemoteChains` cannot be reused
or trivially forked.** A v1.5.0 analogue has to be written. That sequence (~300 lines, with the
three-case supported/remote-token-match logic) is the real bulk of this work and is not in the
brief's deliverables list.

### 0.3 The ops package is code-generated

`burn_mint_token_pool_and_proxy.go` is `// Code generated by operations-gen. DO NOT EDIT.` and
`chains/evm/deployment/operations_gen_config.yaml:15` currently declares only four functions
(`getRemotePool`, `getCurrentInboundRateLimiterState`, `getCurrentOutboundRateLimiterState`,
`getPreviousPool`). New ops go in that YAML, then:

```bash
cd chains/evm && go run ./cmd/operations-gen/main.go -config deployment/operations_gen_config.yaml
```

### Step 2 — `chains/evm/deployment/v1_5_0/sequences/deploy_token_pool.go`

Mirror `v1_5_1/sequences/deploy_token_pool.go`, but the switch has **one** case:

```go

    // ConstructorArgs{Token, Allowlist, RmnProxy, Router} — note: NO LocalTokenDecimals
default:
    return ..., fmt.Errorf("unsupported v1.5.0 token pool type and version: %s", typeAndVersion)
```

the datastore idempotency filter, and `contract.MaybeDeployContract`. Drop the `ERC20Decimals`

### Step 3 — `chains/evm/deployment/v1_5_0/sequences/token_pool/configure_token_pool_for_remote_chains.go`

The load-bearing piece. Fork `v1_5_1/sequences/token_pool/configure_token_pool_for_remote_chains.go`
and apply the ABI delta from §0.2. Keep the overall structure — outer fan-out sequence + inner
per-remote-chain sequence, direct contract bindings (not `ExecuteOperation`) for state reads, for
the stale-cache reason documented there.

Concrete deltas:

1. **Local decimals.** `tp.GetTokenDecimals()` → read `getToken()` then ERC20 `decimals()` via
   `v1_0_0/operations/erc20.GetDecimals`. Feeds `tokensapi.GenerateTPRLConfigs` exactly as before
   — `DoesPoolUseLocalDecimals` already routes `< 1.6.1` down the remote-decimals path
   (`deployment/tokens/rate_limits.go:621`), so no change there.

2. **Remote pool read.** `tp.GetRemotePools(sel)` → `tp.GetRemotePool(sel)`; treat empty bytes as
   "none". Compare against `common.LeftPadBytes(remotePool, 32)` as 1.5.1 does — the left-pad
   rationale (matching what the protocol sends) is unchanged.

3. **Remote pool write.** `AddRemotePool` → `SetRemotePool(sel, paddedAddr)`. **This replaces
   rather than appends** — see [Decision 1](#decision-1--single-remote-pool-cutover-semantics).

4. **`applyChainUpdates`.** Build `[]ChainUpdate` with the 1.5.0 shape
   (`{RemoteChainSelector, Allowed, RemotePoolAddress, RemoteTokenAddress, Outbound…, Inbound…}`).
   Where 1.5.1 passes `RemoteChainSelectorsToRemove: remotesToDel`, emit a **leading
   `allowed:false` entry** for the same selector in the single array, followed by the
   `allowed:true` entry. Verify against the 1.5.0 `TokenPool.applyChainUpdates` implementation
   that remove-then-add in one array is accepted (it iterates the array in order); if it reverts
   with `ChainAlreadyExists`, split into two ops.

5. **Rate-limiter validation.** Keep the 1.5.1 guard verbatim (`IsEnabled && capacity==0 &&
   rate==0` rejected) — same contract lineage, same `validateRateLimiterConfig`.

6. **Type/version read.** `type_and_version.GetTypeAndVersion` is shared; no change.

### Step 5 — Registration + the `IsBurnMintPoolType` gap

`chains/evm/deployment/v1_5_0/adapters/init.go` — add alongside the existing fee adapter:

```go

    chainsel.FamilyEVM, utils.Version_1_5_0, NewTokenAdapter())
```

Both `domains/ccip/resolvers/manager.go` and `domains/ccv/lib/resolvers/manager.go` already import
adapter packages transitively, and `ccip/{mainnet,testnet}/durable_pipelines.go` already import

chainlink-deployments change.** Confirm with the probe in
[token-pool-version-coverage.md §6](token-pool-version-coverage.md).

**Then fix the role-grant gap.** `EVMPoolAdapter.DeployTokenPoolForToken` grants the pool
mint/burn on the token only when `a.IsBurnMintPoolType(input.PoolType)`
(`v1_0_0/adapters/pool_adapter.go:503`), and `utils.IsBurnMintPoolType`
(`deployment/utils/common.go:74`) matches only `BurnMintTokenPool`, `BurnFromMintTokenPool`,
`BurnWithFromMintTokenPool`, `BurnToAddressMintTokenPool`. `BurnMintTokenPoolAndProxy` matches
none of them, so **the grant is silently skipped** and transfers fail only at execution time —
the same class of failure the runbooks call out for partner tokens.

Go embedding gives no virtual dispatch: defining `IsBurnMintPoolType` on the outer v1.5.0
`TokenAdapter` does **not** change what `EVMPoolAdapter.DeployTokenPoolForToken` calls. The fix
must be one of:

1. **(recommended)** add `BurnMintTokenPoolAndProxy` to `deployment/utils/common.go` as a
   `ContractType` constant and to `IsBurnMintPoolType`, **plus** an explicit reject for it in the
   v2.0.0 deploy switch (`v2_0_0/sequences/tokens/deploy_token_pool.go:240`) before the
   `IsBurnMintPoolType` case — otherwise asking for a 2.0.0 `BurnMintTokenPoolAndProxy` silently
   deploys a plain 2.0 `BurnMintTokenPool` instead of erroring;
2. override `DeployTokenPoolForToken` wholesale on the v1.5.0 adapter (duplicates ~100 lines);
3. add a `PoolRoleGrantPredicate func(string) bool` field to `EVMPoolAdapter`, defaulting to
   `utils.IsBurnMintPoolType`.

(1) is smallest and keeps one source of truth. (3) is cleanest if more proxy-shaped pool types
land later.

## 3. Blast radius

Registering an adapter mutates a **process-global singleton** (`tokens.GetTokenAdapterRegistry()`,
`deployment/tokens/product.go:597`). From the moment `v1_5_0/adapters` is imported, every
version-dispatched changeset starts resolving `1.5.0` instead of erroring:

`token_expansion`, `configure_tokens_for_transfers` (including auto-migrate discovery on a 1.5.0
active pool), `manual_registration`, `remove_remote_pools`, `rate_limits`, `configure_token_pool`
(SetTokenPoolAdmins), `revoke/grant_admin_role`, `migrate_lock_release_pool_liquidity`.

This is why full `PoolOps` parity matters, and why `RemoveRemotePools` must return a clear error
rather than a nil write set — a silent no-op there would report success on a pipeline that did
nothing.

Also note the registry ignores duplicate registrations (`if _, exists := …; !exists`), so a
v1.5.0 adapter registered by `init()` cannot be overridden later by a domain.

## 5. Decisions needed before coding

### Decision 1 — single-remote-pool cutover semantics

A v1.5.0 pool stores **one** remote pool per remote chain. The v2 upgrade flow's reverse
propagation (`configure_tokens_for_transfers.go:83-90`) tells peer pools to *add* the new v2 pool
as an **additional** remote so the web stays reachable during cutover; `MigrationMetadata.
LegacyRemotePools` exists precisely for in-flight message protection. A v1.5.0 peer physically
cannot do this — `setRemotePool` replaces.

Options: (a) implement replace semantics, log a loud warning, and document the in-flight gap;
(b) hard-error when a v1.5.0 pool is asked to hold more than one remote pool for a lane, forcing
explicit operator sequencing.

Recommendation: **(a) with a warning**, because (b) makes the two mainnet pools un-upgradable
through the tooling at all, which is the problem we are solving. But the resulting gap is real and
belongs in the upgrade runbook, not just a log line.

### Decision 2 — `RemoveRemotePools`

No `removeRemotePool` on 1.5.0. Nearest equivalent is `applyChainUpdates` with `allowed:false`,
which drops the **entire remote chain config** (rate limits and remote token too), not just one
pool entry. Options: error out (safe, recommended), or implement it as a documented
whole-chain removal. Do **not** implement it as a silent no-op.

### Decision 3 — plain `BurnMintTokenPool 1.5.0`

One testnet pool (Base Sepolia) is recorded as type `BurnMintTokenPool` at version 1.5.0. The
tight scope rejects it, and there are no `gobindings/generated/v1_5_0` bindings for it. Confirm
its on-chain `typeAndVersion()` before deciding — if it reports `BurnMintTokenPool 1.5.0` it will
resolve to the new adapter and then fail in the deploy/configure switch with "unsupported pool
type", which is at least a clear error. Accept that, or widen scope and generate bindings.

### Decision 4 — `IsBurnMintPoolType` fix shape

Options (1)/(2)/(3) in step 5. Recommendation: (1) plus the explicit v2.0.0-switch reject.

## 7. Status — what landed

Implemented on top of `d077fd910`, not the `5c5da7896` baseline the plan was written against.
**That commit ("Add router support to the ConfigureTokenPool changeset") reshaped the extension
point this work plugs into**, so two things in §0–§5 above are now stale:

- `PoolOps.SetAdmins(b, chain, poolAddr, rlAdmin, feeAdmin)` became
  `PoolOps.SetDynamicPoolConfigs(b, chain, poolAddr, router, rlAdmin, feeAdmin)`. The v1.5.0 impl
  therefore also handles the router (`getRouter`/`setRouter`, both present on the v1.5.0 ABI),
  mirroring `poolOpsV151`.
- `tokens.TokenPoolAdminAdapter` was replaced by `tokens.TokenPoolDynamicConfigAdapter`. The
  adapter asserts the new one.

### Deviation from the plan: where the new sequences live

§2 put the deploy sequence in `v1_5_0/sequences` next to the other v1.5.0 sequences, mirroring
v1.5.1. That is an **import cycle**: the deploy sequence needs `v1_0_0/adapters.EVMTokenBase` for
the datastore helpers, and `v1_0_0/adapters` already imports `v1_5_0/sequences` for the
TokenAdminRegistry flow. v1.5.1 has no such constraint because nothing upstream imports
`v1_5_1/sequences`. Both new sequences therefore live in `v1_5_0/sequences/token_pool`, which is a
leaf. Noted in the file header so it is not "tidied" back.

### Regenerating the v1.5.0 operations

`chains/evm/abi/` and `chains/evm/bytecode/**/*.bin` are gitignored build artifacts, and no v1.5.0
ABI was present locally. The inputs were reconstructed from the constants already embedded in the
committed generated file:

```python
abi = re.search(r'BurnMintTokenPoolAndProxyABI = `(\[.*?\])`', src, re.S).group(1)
bin_ = re.search(r'BurnMintTokenPoolAndProxyBin = "([^"]*)"', src).group(1)
# -> chains/evm/abi/v1_5_0/burn_mint_token_pool_and_proxy.json
# -> chains/evm/bytecode/v1_5_0/burn_mint_token_pool_and_proxy.bin
```

Re-running the generator against those reproduced the committed file **byte for byte** before any
config change, which is what validates the reconstruction. Then:

### Found while testing: a pre-existing gas-estimation hazard

Not introduced here, and not fixed here, but worth recording.

`applyChainUpdates` creates a lane's rate limiter buckets with `lastUpdated` = that block's
timestamp. If the next `setChainRateLimiterConfig` is **estimated** while the pending block still
carries the same timestamp, `RateLimiter`'s `timeDiff != 0` refill branch is skipped during
estimation — but it runs when the transaction is actually mined a second later, and the extra
SSTOREs push execution past the estimate. The transaction then fails with `status 0`,
`gasUsed == gasLimit`, and no revert reason.

Confirmed on the simulated backend: bucket `lastUpdated=1789413794`; the update transaction mined
at ts `…795` and ran out of gas at exactly its 53,474 limit, while replaying the identical call
against the parent block succeeded. A retry one block later succeeded, because by then estimation
saw the refill path.

This is a property of the shared pre-2.0 `RateLimiter` plus the estimate-then-mine pattern — v1.5.1
and v1.6.x behave identically. It only bites deterministically on the simulated backend, whose
clock advances exactly one second per block; on a real chain the gas buffer usually absorbs it.
The v1.5.0 rate-limit test advances a block before the update and says why.
